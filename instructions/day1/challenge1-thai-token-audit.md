## เป้าหมายการเรียนรู้

พิสูจน์ด้วยตัวเลขจากข้อมูลจริงว่า **ภาษาไทยกินทรัพยากรมากกว่าภาษาอังกฤษเท่าไหร่** และ **tokenizer ผิดรุ่นให้ตัวเลขผิดแค่ไหน**

## สถานการณ์

ทีมกำลังวางแผนทำ semantic search บนประวัติ ticket ทั้งหมด หัวหน้าถามว่า *"ถ้าจะทำกับ ticket ทั้งระบบ 2,600 อุปกรณ์ จะใช้ทรัพยากรเท่าไหร่ และมีอะไรที่ควรระวัง"*

## สิ่งที่ต้องทำ

### 1. ดึงข้อมูลมา 50 ใบ แล้วแยกกลุ่ม

```sql
SELECT ticket_id, title, description FROM tickets ORDER BY random() LIMIT 50;
```

แยกเป็น 3 กลุ่ม: **ไทยล้วน / อังกฤษล้วน / ปนกัน**
(เกณฑ์ง่ายๆ: นับสัดส่วนอักขระไทยเทียบกับทั้งหมด)

### 2. นับ 3 วิธีเทียบกัน

ใช้ `tokenizer.compare()` แล้วทำตารางนี้:

| กลุ่ม | จำนวนตัวอักษร | คำ (pythainlp) | **token (Gemma)** | token (tiktoken) | tiktoken ผิดกี่ % |
|---|---|---|---|---|---|
| ไทยล้วน | | | | | |
| อังกฤษล้วน | | | | | |
| ปนกัน | | | | | |

### 3. คำนวณอัตราส่วนที่ใช้ตัดสินใจได้จริง

- token ต่อ 1 ตัวอักษร ของแต่ละกลุ่ม
- **token ของข้อความไทย เป็นกี่เท่าของอังกฤษ** เมื่อจำนวนตัวอักษรเท่ากัน
- ถ้าจะ embed ticket ทั้ง 120 ใบ ใช้ token รวมเท่าไหร่

### 4. ประมาณการขึ้น production

สมมติ 2,600 อุปกรณ์ มี ticket เฉลี่ยอุปกรณ์ละ 30 ใบต่อปี

- token รวมต่อปีเป็นเท่าไหร่
- ถ้า embedding ทำได้ ~500 ข้อความ/วินาที ใช้เวลา embed ครั้งแรกนานแค่ไหน
- ถ้าต้อง re-embed ทุกครั้งที่เปลี่ยนโมเดล จะเจอปัญหาอะไร

### 5. เสนอ 1 ข้อ

เสนอวิธีลดต้นทุน 1 ข้อ พร้อมตัวเลขรองรับ

## โบนัส (สำหรับคนทำเร็ว)

1. วัดว่า **การ chunk ด้วยจำนวนตัวอักษร** ให้ token ต่อ chunk แกว่งแค่ไหนระหว่างไทยกับอังกฤษ แล้วเสนอวิธี chunk ที่ดีกว่า
2. หา ticket ที่ token ต่อตัวอักษรสูงที่สุด แล้วดูว่าทำไม (คำเฉพาะทาง? เลขวงจร? ปนภาษา?)
3. เทียบ `newmm` กับ `attacut` ของ pythainlp ว่าตัดคำต่างกันอย่างไร

<details>
<summary>Hint (เปิดเมื่อติดเกิน 10 นาที)</summary>

- แยกภาษาแบบง่าย: `sum(1 for c in text if '฀' <= c <= '๿') / len(text)` > 0.5 ถือว่าไทย
- ถ้าโหลด Gemma tokenizer ไม่ได้ (ออฟไลน์) `tokenizer.count()` จะ fallback เป็นสูตรประมาณ ใช้ได้แต่ต้องระบุในรายงานว่าเป็นค่าประมาณ
- อย่าลืมว่า `description` ยาวกว่า `title` มาก ควรรวมทั้งสองฟิลด์
</details>
